## 💡 Scraping Strategy Answer

**Your Question**: "How will we run scrapers in production? Do I need a continuous service?"

**Answer**:

### Option 1: Scheduled Jobs (Recommended for Start)
**Best for**: Small scale, simple setup
- Use **APScheduler** in your FastAPI backend
- Runs in-process with your main app
- No additional services needed
- Daily scrapes at 3 AM (low traffic time)

```python
# In backend/app/main.py
from apscheduler.schedulers.asyncio import AsyncIOScheduler

scheduler = AsyncIOScheduler()

@scheduler.scheduled_job('cron', hour=3)  # 3 AM daily
async def daily_champion_stats():
    await scrape_and_update_champion_stats()

scheduler.start()
```

**Pros**: Simple, no extra cost, built-in
**Cons**: Scraping blocks main thread if not async, restarts on deploy

### Option 2: Separate Cron Service (Recommended for Production)
**Best for**: Scale, reliability
- **Railway Cron Jobs**: Define schedule in railway.toml
- **Render Cron Jobs**: Separate worker service
- **GitHub Actions**: Scheduled workflow triggers API endpoint

```yaml
# .github/workflows/scrape.yml
name: Daily Scraping
on:
  schedule:
    - cron: '0 3 * * *'  # 3 AM daily

jobs:
  scrape:
    runs-on: ubuntu-latest
    steps:
      - name: Trigger scraping
        run: |
          curl -X POST https://api.tryndraft.com/scrape/trigger \
            -H "Authorization: Bearer ${{ secrets.SCRAPE_API_KEY }}"
```

**Pros**: Reliable, separate from main app, easier monitoring
**Cons**: Slightly more complex setup

### Option 3: Serverless (AWS Lambda)
**Best for**: Cost optimization
- Lambda function triggered by EventBridge (cron)
- Runs only when needed (pay per execution)
- Stores results in S3, then loads to database

**Pros**: No idle costs, auto-scaling
**Cons**: Cold start latency, AWS complexity

### My Recommendation:
**Start with Option 1** (APScheduler), move to **Option 2** (Cron service) when you deploy to production.

**You DON'T need a continuously running scraper** - scheduled daily/weekly scrapes are sufficient!

## 📦 Database Strategy Answer

**Your Question**: "Where and how do we save champion data and user information? Do we need AWS?"

**Answer**:

### Storage Needs
1. **User Data** (profiles, champion pools, draft history)
   - **Where**: PostgreSQL database
   - **Size**: ~1 MB per 1000 users
   - **Backup**: Daily automated backups

2. **Champion Statistics** (win rates, pick rates, matchups)
   - **Where**: PostgreSQL (time-series data)
   - **Size**: ~100 MB for 6 patches of data
   - **Retention**: Keep last 6 patches (auto-delete old data)

3. **Draft Compositions** (training data for neural network)
   - **Where**: PostgreSQL (JSONB columns)
   - **Size**: ~500 MB for 1M drafts
   - **Retention**: Keep last 3 patches

4. **Neural Network Models**
   - **Where**: S3 bucket or similar (model .pt files)
   - **Size**: ~50 MB per model version
   - **Versioning**: Keep last 3 versions

### Do You NEED AWS?
**Short answer: NO!**

### Hosting Options (From Easiest to Most Control)

**Option 1: Railway** (Recommended for start)
- **Database**: PostgreSQL (500 MB free, then $5/month per GB)
- **Backend**: Free tier (512 MB RAM)
- **Redis**: Included
- **Total Cost**: $0-20/month
- **Pros**: Easiest setup, great DX, auto-deploy from GitHub
- **Cons**: Limited free tier, pricing can scale

**Option 2: Render**
- **Database**: PostgreSQL ($7/month for 1 GB)
- **Backend**: Free tier (512 MB RAM, sleeps after 15 min)
- **Total Cost**: $7-25/month
- **Pros**: Simple, good docs, generous free tier
- **Cons**: Paid tier required for always-on

**Option 3: AWS** (Recommended for 1000+ users)
- **Database**: RDS PostgreSQL ($15/month for db.t3.micro)
- **Backend**: EC2 t3.medium ($30/month)
- **Redis**: ElastiCache ($12/month)
- **Storage**: S3 ($3/month)
- **Total Cost**: $60-150/month
- **Pros**: Scalable, professional, full control
- **Cons**: Complex setup, requires AWS knowledge

### My Recommendation:
1. **Start with Railway** (free tier for development)
2. **Move to Railway paid** or Render ($20/month for production)
3. **Scale to AWS** when you have 1000+ users or $100+/month revenue

**You can build and launch the entire product without AWS!**
